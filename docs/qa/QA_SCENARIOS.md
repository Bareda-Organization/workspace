## 0. 시작 전에

### 0.1 데이터를 처음 상태로 되돌리는 법

아래 세 방법 모두 **같은 데이터**로 되돌아간다. 오늘 회차의 시각은 되돌린 그 시각(이하 **T**) 기준으로 다시 잡힌다.

| 방법 | 언제 |
|---|---|
| 관계자 웹 머리말 **[테스트 데이터 초기화]**(로그인 필요 — 내부적으로 `POST /api/v1/dev/reset`) | 스테이징·로컬 — 가장 빠름(약 3초) |
| 백엔드 재기동(`./gradlew bootRun` · 컨테이너 재시작) | 로컬 |
| `docker compose … down` + `up` | 컨테이너 모드 — DB 컨테이너까지 새로 |

- **비밀번호는 전 계정이 같다** — local 은 `password` · staging 은 스테이징 운영자가 `.env` 의 `SEED_PASSWORD_HASH` 로 정한 값(`STAGING.md §6` — 팀원에게 따로 알린다) · demo 는 배포 설정의 값
- 웹·앱 주소와 스테이징 접속은 `docs/backend/infra/STAGING.md`

### 0.2 지도와 Directions 사용량

- QA 서버(local · staging)는 네이버 **Directions 5**(경로 `/map-direction/v1/driving` · 지점 상한 7)로 도로 경로를 받는다. 노선 하나가 학원 + 승하차지 10곳 = 11지점이라 **확정 1회 = 호출 2회**
- 초기화 1번 뒤 2시간 30분 안에 확정되는 회차는 4개 → **약 8회 호출**. 초기화를 짧은 간격으로 반복하지 않는다
- 시드에 들어 있는 지난·운행 중 회차의 도로 경로는 미리 받아 둔 실제 경로(하원은 등원 경로를 거꾸로 사용)
- **지도의 버스 움직임** — 로컬 시뮬레이터가 기사 단말 대신 2초마다 위치를 올림
  - 학원 B: 확정된 회차를 **자동 출발**시키고 노선을 따라 주행
  - 학원 A: 자동 출발 없음(매니저 앱으로 출발). 이미 운행 중인 회차만 위치 송신
  - 시뮬레이터 버스는 노선 첫 지점부터 출발 — 운행 중 회차의 "이미 지난 승하차지" 와 지도 위치가 다를 수 있음

### 0.3 지금 탑승하는 학생의 보호자 찾기

오늘 탑승자는 **요일마다 다르다**(수업 요일 묶음, §2.4). 아래 계정은 해당 요일에 반드시 타는 학생의 보호자다. 결석으로 잡혔으면(약 4%) 관계자 웹 회차 명단에서 다른 학생을 고르고, 학생 상세의 보호자 아이디로 로그인한다.

|---|---|---|
| A 1호차 | `parentA2` 차혜원 — 구로운(초4, 반달마을 극동) | `parentA6` 천석진 — 천하준(초4, 반달마을 선경) |

## 6. 알려진 한계

- **학생 사진 없음** — 사진 파일 저장소가 시드 밖. QA-STF-04 로 직접 올려 확인
- **문자(SMS)** — 발송기가 설정되지 않으면 아이디·비밀번호 찾기는 "이용 불가" 응답. 개발용 로그 발송기(`app.sms.sender=logging`)는 번호 끝 4자리와 글자 수만 기록
- **푸시(FCM)** — 키 부재. 앱 알림은 알림 목록으로 확인. 시드 알림의 "발송됨" 표시는 시드 값
- **오늘 회차 시각** — 초기화 시각 기준이라 실제 수업 시각(§2.5)과 다름. 정시 운영은 내일 회차 · 지난 이력에서 확인
- **시뮬레이터 위치** — 노선 처음부터 주행. 운행 중 회차(B 1호차)는 이미 지난 승하차지와 지도 위치가 어긋날 수 있음
- 결석 · 미승차 학생은 회차마다 정해진 규칙(hashtext)으로 고름 — 같은 초기화 방식이면 같은 학생
