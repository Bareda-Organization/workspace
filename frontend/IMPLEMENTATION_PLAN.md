### 1.1 앱 하나가 여러 역할을 담음 — 역할 분기 규칙 (2026-09-10 사용자 확정)

**앱을 역할마다 만들지 않고, 앱 하나가 로그인 결과의 역할로 갈라짐.**

| 앱 | 담는 역할 | 갈리는 지점 | 공유하는 것 |
|---|---|---|---|
| `parent-app` | 학부모 · **학생** | 로그인 후 진입 라우트 · 탭바 구성 · 쓰기 권한 | 화면·위젯 대부분 |
| `manager-app` | 버스기사 · **동승자** | 회차 화면의 조작 권한 · 탭바 구성 | 화면·위젯 대부분 |

**갈리는 것은 화면이 아니라 권한과 진입점.** 같은 화면을 두 벌 만들지 않음.

- **학생은 조회 전용** (`UF-S-01`) — 학부모 화면을 그대로 쓰되 등원 여부 변경 · 탑승 위치 변경
  진입점을 감춤. 학생 전용은 부모 연결 코드 생성(`S-05` · `§3.3`) 하나
- **기사와 동승자는 조작 권한이 갈림** (`UF-D-*` ↔ `UF-E-*`) — 기사는 도착·지연 알림 전송,
  동승자는 개인별 승하차 상태 결정. 같은 `StopRoster` 화면에서 **버튼 노출이 갈림**
- 분기는 화면 안 `if` 가 아니라 **`core/auth` 의 역할 정책 한 곳**에서 판정하고 화면은 그 결과만 받음
  — 화면마다 조건문을 흩으면 권한 규칙이 어디 있는지 알 수 없게 됨

⚠ **두 앱을 하나로 더 합치지 않음 — 2026-09-10 사용자 확정.** 매니저 앱은 운행 내내
**위치 권한(백그라운드)과 오프라인 큐**가 필요함(`M-06` · `§4.12`). 학부모 앱에 합치면
학부모 단말에도 그 권한을 요구하게 되고, 스토어 심사와 사용자 신뢰 양쪽에서 값을 치름.
대상 사용자도 고객(학부모·학생)과 운영 인력(기사·동승자)으로 갈림.

**따라서 Flutter 앱은 2개이고, 각 앱 안에서 역할 2종으로 갈라짐.** 위 표가 그 전부.

## 2. 디렉터리 구조

```
frontend/
├── CONVENTIONS.md              React/TypeScript 컨벤션
├── CONVENTIONS_FLUTTER.md      Flutter/Dart 컨벤션
├── IMPLEMENTATION_PLAN.md      이 문서
├── design-system/              claude.ai 디자인 시스템 사본 (읽기 전용)
├── packages/
│   └── baraeda_ui/             Flutter 공용 위젯 패키지 — 두 앱이 의존
└── apps/
    ├── academy-web/            Next.js (관계자 + 메인 관리자)
    ├── parent-app/             Flutter
    └── manager-app/            Flutter
```

각 앱 내부 구조는 컨벤션 문서가 정본 —
웹은 `CONVENTIONS.md` "디렉터리" 절, Flutter 는 `CONVENTIONS_FLUTTER.md` §2·§3.
둘 다 **기능(도메인) 하나 = 폴더 하나**이고 **기능끼리 서로 import 하지 않는 것**이 확장의 근거.

`design-system/` 은 **읽기 전용 사본**. 고칠 일이 생기면 원격 프로젝트를 고치고 다시 내려받음
— 로컬에서 직접 고치면 다음 동기화에 덮임.

### 2.1 ⚠ `design-system/ui_kits/` 를 앱에서 import 하지 않음

킷의 `*Screens.jsx` · `kit.jsx` 는 **브라우저로 생김새를 보는 클릭 스루 시안**이고 앱 코드가 아님.
`김하준` · `3-2호차` · `대치사거리` 같은 값이 파일 안에 박혀 있는 것은 그 용도 때문.

| 무엇 | 어디 | 데이터 출처 |
|---|---|---|
| 시안 | `design-system/ui_kits/` | 값이 박혀 있음. **읽기 전용 참조** |
| 실제 화면 | `apps/*/features/` | **API 응답** — `API_SPEC` 계약 |
| 시험 데이터 | 각 앱 테스트 디렉터리 | 테스트 안에서만. 화면 코드에 섞지 않음 |

- 시안의 값을 앱 코드로 옮겨 붙이지 않음. **보는 것은 배치·간격·문면이고 데이터가 아님**
- 화면은 로딩·성공·실패 세 갈래를 전부 그림. 시안에는 성공 갈래만 있음
- `window.DesignSystem_9e66e1` · `window.MapSurface` 같은 전역 참조는 **시안 실행 방식**이며
  앱에서는 쓰지 않음

## 4. ⚠ 디자인 킷과 정본의 어긋남 — 착수 전에 가름

디자인 시스템은 **구 기획 PDF + 유저플로우 이미지**만 근거로 만들어졌고(`design-system/readme.md`
의 "출처" 절), `docs/` 4종 재작성 이후 갱신되지 않음. 확인된 어긋남:

| # | 디자인 킷 | 정본 | 판정 |
|:-:|---|---|---|
| 1 | *"아이디/비밀번호 없이 **부여된 코드 6자리**로만 로그인"* (`parent-app/README.md`) | `API_SPEC §2.2` 회원가입 + `§2.5` 로그인. **코드는 로그인 수단이 아니라 자녀 연결 수단**(`§3.4` · UF-P-01) | **정본이 이김.** 로그인 화면을 다시 설계 |
| 2 | 관계자 웹 7화면 | API §5 는 45개 엔드포인트 · 기능 ID A-01~17 | **킷이 사양의 절반을 안 덮음.** 부재 화면 7종을 새로 설계 |
| 3 | 매니저 앱 7화면 | M-15 비상 알림 · M-06 오프라인 큐 부재 | 화면 2종 신설 |
| 4 | 메인 관리자 콘솔 | O-01~07 · API §6 | 킷 전체 부재 |

**이 어긋남은 결함이 아니라 시점 차이.** 디자인 킷은 구 기획 시점에서 멈춰 있고 정본은 그 뒤에 바뀜.

**처리 방식 (2026-09-10 사용자 확정)** — 시안을 기다리지 않고 **구현하면서 설계함.**
디자인 시스템의 토큰·규칙·색을 근거로 부재 화면을 유도하며, 지킬 것과 하지 않을 것은 §8.1 에 있음.
어긋남 1번(로그인)은 **정본대로 다시 만듦** — 킷의 코드 로그인 화면을 그대로 옮기지 않음.

**백엔드 1대**(로컬 8080). 포트를 미리 배정하고 발주문에 적음.

### 5.0 F2 — 공통 인증 (착수 전 고정한 목표 표)

**정본** — `API_SPEC §2`(11개) · `§1.2.1`(refresh 전달 수단) · `§1.4`(계정 상태 게이트) ·
`USER_FLOWS UF-X-01 ~ UF-X-04`. **수치·문자열은 이 표를 믿지 말고 정본에서 다시 세라.**

#### 왜 여기만 순차인가
제품 3개가 전부 이 위에 선다. 갈라서 만들면 **토큰 저장·재발급·상태 게이트가 세 벌**이 되고,
그중 하나만 고치는 사고가 뒤에 남는다. 공통분을 먼저 세우고 나서 F3 에서 3갈래로 갈라진다.

#### ⚠ 앱과 웹이 갈리는 지점 — 여기서 틀리면 로그인이 조용히 샌다

| 항목 | 앱 (Flutter 2개) | 웹 (Next.js) |
|---|---|---|
| `X-Client-Type` | `app` (미전달 시 기본값이지만 명시) | `web` |
| 서버 → 클라이언트 refresh | 응답 **본문** `refresh_token` | **`Set-Cookie`** — 본문에 담지 않음 |
| 클라이언트 → 서버 refresh | 요청 **본문** | 쿠키 자동 동봉 (`credentials: include`) |
| access 보관 | 기기 보안 저장소 | **메모리에만** |
| 자동 로그인 | 앱 재실행 시 저장된 refresh 로 재발급 | **새로고침마다 재발급이 정상** — 메모리라 사라짐 |

**웹 쿠키 속성 4개는 전부 필수이고 하나라도 빠지면 결함** — `HttpOnly` · `Secure` ·
`SameSite=Strict` · `Path=/api/v1/auth`. `Path` 는 베이스 경로(`/api/v1`)를 포함해야
`/api/v1/auth/refresh` 에 실제로 동봉된다. `Secure` 는 `http://localhost` 에서도 유지한다
(브라우저가 보안 컨텍스트로 취급).

#### ⚠ 계정 상태 게이트 — `pending` 이 부를 수 있는 것은 4개다

| 상태 | 로그인 | 허용 |
|---|---|---|
| `pending` | 성공(토큰 발급) | `GET /auth/signup-status` · `POST /auth/logout` · **`GET /me`** · **`POST`·`DELETE /me/devices`** |
| `rejected` | 성공 | 위 + `POST /auth/signup/reapply` |
| `active` | 성공 | 역할별 권한 범위 |
| `blocked` | **실패** `403 AUTH_ACCOUNT_BLOCKED` | 부재 — 해제는 메인 관리자만 |

⚠ **정본이 스스로 정정한 자리다.** 이 표가 원래 `pending` 을 "2개만" 으로 적었다가
`§2.10`·`§2.11` 과 모순이 드러나 바로잡혔다. **`/me` 가 없으면 앱 재실행 후 역할·상태를
다시 얻을 수단이 없어 대기 화면 분기 자체가 성립하지 않고**, `/me/devices` 가 없으면
승인 결과 푸시를 받을 단말이 등록되지 않는다. **"2개" 라고 적힌 옛 서술을 보면 무시하라.**

### 8.3 지도 SDK — 네이버 단일 공급자 (2026-09-10 사용자 확정)

공급자는 `docs/` 에서 이미 네이버로 확정돼 있었고, 이번에 **웹·Flutter 양쪽 SDK 를 네이버로** 고정.
공급자가 하나면 지도 키와 사용량 관리가 한 곳으로 모이고, 두 제품의 지도 표현이 갈리지 않음.

| 대상 | 채택 | 비고 |
|---|---|---|
| 관계자 웹 | **Naver Maps JavaScript API v3** | React 공식 래퍼 부재 — 얇은 훅으로 직접 감쌈 |
| Flutter 2앱 | **`flutter_naver_map`** | 네이버 공식 네이티브 SDK 래퍼. 1.4.4 · Android 6.0(SDK 23) / iOS 12.0 이상 · BSD-3-Clause |

**Google Maps 를 버린 이유** — 한국 도로 데이터가 제한돼 길찾기·상세 지도가 반쪽. 국내 서비스에 부적합.

#### ⚠ 연동(F4) 착수 전에 확인할 것 2가지

1. **인증 방식이 이관 중이다.** `flutter_naver_map` 1.3.1 부터 네이버 클라우드 플랫폼 변경으로
   **신규 인증 API 가 추가**됐고, 옛 방식은 2025-07-01 부터 무료 이용량 제공이 중단됨.
   초기화는 `FlutterNaverMap().init(clientId: …, onAuthFailed: …)` 형태이나
   **키 발급 절차와 파라미터 이름을 네이버 문서에서 직접 확인하고 착수한다.**
   웹 JS API v3 도 같은 이관의 영향을 받으므로 함께 확인
2. **버스 마커 애니메이션 지원이 미확인.** 디자인 시스템은 *"버스 마커는 깜빡이지 않고
   **위치만 600ms 로 보간**"* 을 규정하는데, `flutter_naver_map` 문서에 마커 위치를
   애니메이션으로 옮기는 API 가 서술돼 있지 않음(정적 `addOverlay` 예시만 존재).
   **F4 첫 작업은 이 기능의 실재 확인**이고, 없으면 좌표를 직접 보간해 갱신하는 방식으로 대체하며
   그때 프레임 끊김이 눈에 보이는지 실측한다

패키지 최종 게시가 8개월 전이라 **Flutter 3.44.8 과의 호환은 F4 착수 시 실제 빌드로 확인**한다.

#### 8.3.1 요금 때문에 공급자를 바꿀 수 있다 — 그래서 지도를 포트 뒤에 둔다

사용자 지시(2026-09-10): *"무료 이용이 안 된다면 티맵으로 변경하는 것도 고려"*.

**요금은 확인하지 못했다** — 조율자가 네이버 클라우드 플랫폼 요금 페이지를 열었으나 본문을 받지 못했다.
**F4 착수 전에 요금 페이지에서 월 무료 제공량과 초과 단가를 직접 확인하고 판정한다.**

⚠ **앞서 인용한 "2025-07-01 무료 이용량 제공 중단"은 옛 인증 방식에 대한 것**이고
네이버 지도 전체가 유료로 바뀐다는 뜻이 아니다. 신규 인증 API 로 옮기는 것이 전제.

**티맵으로 바꿀 때의 실제 비용 (실측 2026-09-10)** — pub.dev 검색 결과 **티맵 지도를 렌더링하는
Flutter 패키지가 부재**하다(경로탐색 REST 래퍼조차 없음). 즉 티맵을 쓰면 앱 2개에서
**네이티브 SDK 를 platform channel 로 직접 감싸거나 WebView 로 띄워야** 하고,
후자는 `§8.3` 2번의 마커 보간 요구를 더 어렵게 만든다. 웹은 티맵 JS SDK 가 있어 부담이 덜하다.

**그래서 구현 규칙 하나를 고정한다 — 지도를 포트 뒤에 둔다.**

| 스택 | 자리 | 화면이 아는 것 |
|---|---|---|
| 웹 | `features/map/` 의 인터페이스 1개 | 좌표·정류장·버스 위치. **SDK 이름을 모른다** |
| Flutter | `packages/baraeda_ui` 가 아니라 각 앱 `core/map/` 의 추상 위젯 | 같음 |

- **화면 코드가 `NaverMap` · `NMarker` 같은 SDK 타입을 직접 쓰지 않는다.** 어댑터 안에서만 쓴다
- 디자인 시스템의 `MapSurface` 가 이미 이 모양이다 — *"실제 SDK 타일이 들어갈 자리"*
- 이렇게 두면 공급자 교체가 **어댑터 1개 교체**로 끝나고, 화면 20여 개를 건드리지 않는다
- 교체 가능성이 실재하므로 이것은 과설계가 아니다

### 8.1 디자인이 부재한 화면을 만들 때 지킬 것

킷에 없는 화면(관계자 웹 7종 · 메인 관리자 8종 · 매니저 앱 2종)은 새로 설계하되,
**임의로 만들지 않고 디자인 시스템의 규칙을 근거로 유도함.**

| 근거 | 위치 |
|---|---|
| 색 · 상태 색 매핑 · 화이트 셸 규칙 | `design-system/readme.md` VISUAL FOUNDATIONS · `tokens/semantic.css` |
| 타입 · 여백 · 모서리 · 그림자 · 모션 | 같은 문서 · `tokens/*.css` |
| 카피 문면 (어미 · 시각 표기 · 버튼 라벨) | 같은 문서 CONTENT FUNDAMENTALS |
| 화면 골격 (헤더 56 · 사이드바 248 · 본문 최대 1160) | 같은 문서 여백·레이아웃 |
| 비슷한 화면의 구성 | 기존 킷 7화면 (`WebScreens.jsx`) |

**하지 않을 것** — 배경 이미지·그라디언트·블러 · 이모지 · 왼쪽 컬러 보더 카드 ·
바운스 애니메이션 · 파란 하이라이트. 전부 디자인 시스템이 명시적으로 금지한 것.
